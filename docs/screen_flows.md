# 화면 흐름과 와이어프레임

PlanTogether iOS 앱의 화면 목록, 이동 구조, 화면별 저해상도 와이어프레임과 상태(로딩·빈·대기·오류·오프라인)를 정한다. 시각 규칙은 `docs/design_system.md`, 레퍼런스 분석은 `docs/design_references.md`다.

- 상태: 초안 확정(2026-10-29). 1단계 문서. 코드 적용은 `design_system.md` §9.3 순서
- 화면은 체크리스트 1~10의 기능에만 있다. 새 기능을 더하지 않는다
- 화면 문구 중 상세 설계에 정해진 것은 그대로 옮겼다(출처 표기). 나머지는 제안 문구다
- 와이어프레임의 `[ 버튼 ]`은 Primary, `( 버튼 )`은 Secondary, `버튼 ›`은 Tertiary 또는 이동 행이다

---

## 1. 탭 구조와 이동 지도

### 1.1 권장: 탭 3개 `Party · 약속 · 나`

지금은 `Party · 캘린더 · 활동 시간 · 설정` 4개다(`RootView.swift`). 캘린더 연결과 활동 시간은 한 번 설정하면 자주 열지 않는다. 대신 제안·확정이 생기면 여러 Party의 약속을 한곳에서 볼 곳이 필요하다.

```
┌─ 로그인 전 ────────────────────────────────────────────────┐
│ 환영 → 로그인 ⇄ 가입 → 인증 코드                          │
│              └→ 비밀번호 재설정(이메일 → 코드+새 비밀번호) │
└────────────────────────────────────────────────────────────┘
                         │ 세션
┌─ 탭 바 ────────────────┼───────────────────────────────────┐
│ [Party]                [약속]                 [나]          │
│  Party 목록             약속 목록              나(설정)     │
│   ├ 준비 카드 ─────────────────────────────▶ 캘린더 연결  │
│   │                                         ▶ 활동 시간    │
│   ├ + 새 Party (시트)                         알림 설정     │
│   ├ + 초대로 참여 (시트, 임시)                프로필        │
│   └ Party 상세                                로그아웃      │
│      ├ 모두 가능한 시간 찾기 → 결과 → 제안 작성 계정 삭제  │
│      ├ 직접 시간 정하기 → 제안 작성                         │
│      ├ 제안 상세(응답)  ◀──────── 약속 목록에서도           │
│      ├ 확정 약속 상세   ◀──────── 약속 목록에서도           │
│      ├ 멤버(관리)                                           │
│      ├ 초대 링크                                            │
│      └ 내 일정 공개                                         │
└────────────────────────────────────────────────────────────┘
초대 Universal Link ─▶ (로그인 필요 시 로그인) ─▶ 초대 미리보기 ─▶ Party 상세
알림 탭 ─▶ 제안 상세 / 확정 약속 상세 / Party 상세 (역조회 실패 시 Party 목록, 설계 9 §9.3)
```

- **약속 탭**은 sync 캐시에 이미 있는 `proposal`·`proposal_response`·`confirmed_event`를 Party를 가로질러 모아 보여 줄 뿐이다. 새 서버 API나 데이터가 없다.
- **나 탭**은 지금의 캘린더·활동 시간·설정 탭을 합친 것이다. 화면 자체(`CalendarSection`, `PreferencesView`)는 그대로 옮긴다.
- 활동 시간·캘린더는 Party 목록의 "준비" 카드와 검색의 본인 CTA에서도 바로 열린다. 탭을 줄여도 찾기 어려워지지 않는다.

### 1.2 대안: 탭 2개 `Party · 나`

- 제안·확정 약속은 Party 상세 안에만 있다. Party 목록 카드의 "다음 할 일" 줄과 설계 9 §9.4의 미해결 개수 배지로 응답이 필요한 것을 알린다.
- 장점: 가장 단순하다. 단점: Party가 여러 개면 응답할 제안을 찾으러 Party를 하나씩 열어야 한다.
- 탭 구성은 사용자 취향 결정이다(rec `2026-10-29_*_design_system.md` "사용자 결정 필요").

## 3. 로그인·가입·인증 코드·비밀번호 재설정 (S1~S5)

> **소유와 순서:** 로그인 화면은 이메일 로그인 작업(`feature/email-login`, 병합 대기)이 지금 바꾸고 있다. 이 절은 그 계약(설계 2 §5.1 개정)에 맞춘 디자인이다. 2단계에서는 그 브랜치가 `main`에 들어온 뒤 뷰만 바꾼다.

### 지켜야 할 문구 계약 (이메일이 있는지 드러내지 않는다)

- 가입·코드 재전송·재설정 요청은 결과와 상관없이 같은 안내 하나: `메일을 보냈습니다. 받은 편지함에서 6자리 코드를 확인하세요.` "이미 가입된 이메일", "없는 계정" 같은 문구는 없다.
- 로그인 실패는 원인과 상관없이 하나: `이메일 또는 비밀번호가 맞지 않습니다.` 예외는 `email_not_verified` 하나로, 문구 없이 인증 코드 화면으로 보낸다.
- 코드 실패(`invalid_code`)는 원인과 상관없이 하나: `코드가 맞지 않거나 만료됐습니다. 코드를 다시 받아 주세요.`
- 비밀번호 규칙 위반(`weak_password`): `비밀번호는 10자 이상이어야 합니다.` 조합 규칙과 강도 막대는 없다.
- 요청 제한(429): `잠시 후 다시 시도해 주세요.` `Retry-After`가 있으면 남은 시간을 쓴다.

### S4 인증 코드

```
┌───────────────────────────────┐
│ ‹  메일을 확인하세요            │
│ 메일을 보냈습니다. 받은 편지함 │
│ 에서 6자리 코드를 확인하세요.  │
│ name@example.com               │
│ ┌──┐┌──┐┌──┐┌──┐┌──┐┌──┐      │  ← oneTimeCode, 붙여넣기 지원
│ │ 4││ 8││ 1││  ││  ││  │      │
│ └──┘└──┘└──┘└──┘└──┘└──┘      │
│ 코드는 1시간 동안 유효합니다.  │
│ [          확인             ] │  → email+password+code → 세션
│        코드 다시 받기 ›        │  → 30초 뒤 활성
└───────────────────────────────┘
```

- 인증 요청은 이메일 + 비밀번호 + 코드다. 비밀번호는 S3(또는 S2의 `email_not_verified`)에서 화면 상태로 들고 온다. 앱이 꺼져 비밀번호가 없으면 비밀번호 필드를 함께 보인다.
- 실패는 `invalid_code` 한 문구. 5번 틀리면 코드가 무효가 되므로 같은 문구 아래 `코드 다시 받기`를 Secondary로 올린다.
- 성공하면 세션을 받고 Party 목록으로 간다.

```
│ └──────────────────────┘ │    │ 새 비밀번호 (10자 이상)   │
│ [   재설정 코드 받기   ] │ ─▶ │ ┌──────────────────┬───┐ │
```

## 4. Party 목록 (S6)

```
┌───────────────────────────────┐
│ 내 Party                  ＋  │  ← ＋: 새 Party / 초대로 참여
│ ┌───────────────────────────┐ │
│ │ 준비  1/2                 │ │  ← 본인 준비만. 끝나면 사라짐
│ │ ✓ 캘린더 연결             │ │
│ │ ○ 활동 시간 정하기     ›  │ │
│ └───────────────────────────┘ │
│ ┌───────────────────────────┐ │
│ │ ┌──┐ 주말 등산 모임       │ │
│ │ │주│ 멤버 4명 · 방장      │ │
│ │ └──┘                      │ │
│ │ ● 내 응답이 필요한 제안 1개›│ │
│ └───────────────────────────┘ │
│ ┌───────────────────────────┐ │
│ │ ┌──┐ 스터디               │ │
│ │ │스│ 멤버 3명             │ │
│ │ └──┘                      │ │
│ │ 11월 2일 (일) 오후 2:00   │ │  ← 다음 확정 약속
│ │ GMT+9                     │ │
│ └───────────────────────────┘ │
├───────────────────────────────┤
│  Party      약속 (1)     나    │  ← 미해결 개수 배지(설계 9 §9.4)
└───────────────────────────────┘
```

- **준비 카드**는 본인의 캘린더 연결 상태(`ready`인지)와 활동 시간 저장 여부만 본다. 둘 다 끝나면 사라진다. 다른 멤버의 준비 상태는 없다.
- **미해결 개수 배지**: 설계 9 §9.4의 미해결 `calendar_write_command`·`calendar_cleanup_suggestion` 개수다. 권장 탭안에서는 약속 탭 배지, 대안에서는 목록 상단 배너. 여기에 내 응답이 필요한 제안 수를 더할지는 2단계에서 정한다(본인 데이터라 허용).
- Party 카드 규칙은 `design_system.md` §5.2.

| 상태 | 표시 |
|---|---|

|---|---|

| 오류 | 섹션별 재시도 줄 |
| 오프라인 | 로컬 내용 + 오프라인 배너. 검색·초대·관리 동작 비활성 `연결이 필요합니다` |
| 가입 전 생성된 제안 | 카드에 `가입 전에 생성된 제안` 칩, 응답 표시 없이 읽기 전용(설계 7 §4.1) |

### S9 멤버·관리

```
┌───────────────────────────────┐
│ ‹  멤버 4명                    │
│ (나) 나 · 방장                 │
│      캘린더 연결됨             │  ← 본인 행에만 캘린더 상태
│ (민) 민지                  ⋯  │  ← 방장에게만 ⋯ : 내보내기
│ (지) 지호                  ⋯  │
│ (서) 서연                  ⋯  │
│ ───────────────────────────── │
│ 소유권 넘기기 ›                │  ← 방장만
│ ───────────────────────────── │
│ Party 나가기                   │  ← error 글자, 맨 아래
│ Party 해산                     │  ← 방장만
└───────────────────────────────┘
```

- 방장의 `Party 나가기`: 다른 멤버가 있으면 `방장은 소유권을 넘긴 뒤에 나갈 수 있습니다` + `소유권 넘기기`로 보낸다. 혼자면 문구가 `Party 해산`으로 바뀐다(설계 4 §3.5).
- 일반 멤버 나가기 확인: `나가면 내 일정 정보가 이 Party에서 삭제됩니다.`
- 위임 확인: `넘긴 뒤에는 되돌릴 수 없고 관리 권한을 잃습니다.`(설계 4 §3.4)
- 강퇴 확인: 사유 입력 없음(설계 4 §7.3).
- 해산: Party 이름을 직접 입력해야 `해산` 버튼이 켜진다.
- 진행 중인 제안이 있으면 나가기·강퇴 확인에 `진행 중인 제안은 다시 제안해야 합니다`를 더한다(설계 7 §4.1 `reproposal_required`).
- 오프라인: 목록은 보이고 관리 동작 전부 비활성(설계 4 §8.2, 일반 멤버 나가기만 큐 허용).

- 상세 공개로 올리면 `202 pending_details_refresh`: 대기 배너 `제목 공유를 준비하는 중입니다. 그동안은 시간만 공개됩니다.`(설계 5 §4.2)
- 오프라인: 선택 행 비활성 + `개인정보 설정은 연결된 상태에서만 바꿀 수 있습니다`(큐 금지, 설계 5 §4.2).
- 409 version: 서버 값을 다시 읽어 보여 주고 `다른 기기에서 바뀐 설정을 불러왔습니다`.

```
① 설명                      ② 시스템 권한            ③ 읽을 캘린더

│ • 일정 제목·장소·메모는  │  └────────────────────┘  │ 캘린더를 고르세요.      │
│   서버에 올리지 않아요   │                          │ ☐ 개인     iCloud      │
│ • 시작·끝 시각만 올려요  │                          │ ☐ 회사     Exchange    │
│ • 공개 수준은 Party마다  │                          │ ☐ 가족     iCloud      │
│   정해요                │                          │ 처음에는 아무것도 선택 │
│ [   캘린더 연결하기   ]  │                          │ 하지 않은 상태입니다.  │

                                                    └────────────────────────┘
④ 확정 약속을 넣을 캘린더        ⑤ 상태
┌────────────────────────┐  ┌──────────────────────────────┐
│ ‹ 약속을 저장할 곳      │  │ ‹ 캘린더                      │
│ ◉ PlanTogether 캘린더   │  │ ● 준비됨  2분 전 업데이트     │
│   새로 만들기 (권장)    │  │ 읽는 캘린더 2개           ›   │
│ ○ 개인                  │  │ 약속 저장   PlanTogether  ›   │
```

- ①의 문구는 설계 3 §5.1(목적과 서버에 저장되는 최소 데이터 설명)을 따른다. ③은 기본 선택 없음, 하나 이상 골라야 `다음`이 켜진다.
- ④는 설계 8(쓰기, 체크리스트 8) 구현 때 붙인다. 그 전에는 ③에서 끝난다.

| `source_status` | 배지·문구 | 행동 |
|---|---|---|
| `syncing` | `● 올리는 중` 진행 표시 | 마지막 정상 데이터 유지 |
| `ready` | `● 준비됨` + 마지막 업데이트 | `지금 새로고침` |
| `stale` | 경고 배너 `내 캘린더 정보가 오래됐습니다` | `내 캘린더 새로고침` |
| `denied` | 오류 배너 `캘린더 접근이 꺼져 있습니다` | `설정 앱 열기` |
| `restricted` | `이 기기에서는 캘린더 접근이 제한돼 있습니다` | 없음(다시 요청하지 않음) |
| `revoked` | `캘린더 접근이 해제되어 공통 시간 계산에서 빠졌습니다. 7일 안에 다시 연결하지 않으면 올린 시간 정보가 삭제됩니다.` | `다시 연결` |
| `needs_source_reselection` | `읽던 캘린더를 찾을 수 없습니다` | `캘린더 다시 고르기` |
| `error` | `캘린더를 올리지 못했습니다` | `다시 시도` |
| 다른 기기가 동기화 중 | `다른 기기가 캘린더를 맞추고 있습니다` | `이 기기로 가져오기` |

- **권한이 없거나 선택한 캘린더가 없는 상태를 "일정 없음"으로 보이지 않는다**(설계 3 §5.2).
- `시연 일정 만들기 (DEBUG)`는 DEBUG 빌드에만 남긴다.

## 10. 활동 시간 (S14)

지금 화면(`PreferencesView`)의 구조를 유지하고 `Form`에 테마만 입힌다.

```
┌───────────────────────────────┐

│ 약속을 잡아도 되는 시간대예요. │
│ 다른 멤버에게 보이지 않아요.   │
│ 시간대   서울 (GMT+9)       › │
│ 월  09:00 ~ 22:00           › │

│ …                              │
│ 토  10:00 ~ 02:00 다음 날   › │
│ 일  활동 안 함               › │
│ [          저장             ] │
```

- "다른 멤버에게 보이지 않아요"는 설계 6이 활동 시간을 본인만 다루는 데 근거한다.

```
│ (14일) (60분) (서울 GMT+9) 편집│   │ (14일) (60분) (서울 GMT+9) 편집│
│                               │   │ ┌───────────────────────────┐ │
│ 10월 30일 (목)            ✦   │   │ │ ⏳ 그룹 준비를 기다리는 중 │ │
│ ┌───────────────────────────┐ │   │ │ 내 활동 시간을 먼저       │ │
│ │ 오전 10:00 – 11:00 GMT+9 ›│ │   │ │ 설정해 주세요.            │ │
│ │ 오후 2:00 – 3:00   GMT+9 ›│ │   │ │ ( 내 활동 시간 설정 )     │ │  ← 본인 원인일 때만
│ │ 오후 7:30 – 8:30   GMT+9 ›│ │   │ └───────────────────────────┘ │
│ └───────────────────────────┘ │   │                               │
│ 10월 31일 (금)                 │   │ (다른 사람이 원인이면)        │
│ ┌───────────────────────────┐ │   │ ⏳ 그룹 준비를 기다리는 중    │
│ │ 오후 6:00 – 7:00   GMT+9 ›│ │   │ 다른 멤버의 준비가 끝나면     │
│ └───────────────────────────┘ │   │ 다시 찾을 수 있습니다.        │
│ 오후 3:40까지 유효한 결과입니다│   │ ( 다시 찾기 )                 │
└───────────────────────────────┘   └───────────────────────────────┘
```

- 조건 칩을 누르면 조건 시트(기간 시작일·일수, 길이, 시간대)가 열린다. 기본 오늘 포함 14일·60분(rec `1421`).
- 화면 제목 `모두 가능한 시간`, 날짜 섹션, 하루 최대 3개, 지역 시각 + 약식 시간대(설계 6 §8).
- 슬롯을 누르면 S16 제안 작성으로 간다. `calculationVersion`과 검색 조건을 함께 넘긴다(설계 6 §8).
- ✦는 결과가 처음 나타날 때 한 번 튀는 반짝임이다(`design_system.md` §4.4).

| 상태 | 표시 |
|---|---|
| 찾는 중 | 날짜 섹션 skeleton 2개 + `찾는 중…` |
| 결과 0개 | 빈 상태 `선택한 기간과 활동 시간 안에 모두 가능한 시간이 없습니다` + `[기간·길이 바꾸기]`(설계 6 §8) |
| 준비 대기 | 대기 배너 `그룹 준비를 기다리는 중`. 본인 원인별 CTA: 활동 시간 미설정 `내 활동 시간 설정`, 캘린더 미연결 `캘린더 연결`, 올리는 중 진행 표시, 오래됨·오류 `내 캘린더 새로고침`, 권한 거부·철회 `설정 앱 열기`, 읽을 캘린더 없음 `캘린더 고르기`(rec `1421` `CalendarCTA`) |
| 결과 만료 | 마지막 줄이 경고로 `결과가 만료됐습니다. 다시 찾아 주세요.` + `다시 찾기`. 슬롯은 흐리게, 눌러도 제안으로 가지 않는다 |
| 그룹이 바뀜(409 `availability_changed_retry`) | 한 번 자동 재시도, 또 그러면 `그룹 정보가 바뀌었습니다. 다시 찾아 주세요` |
| 검증 오류 | 조건 시트 안 필드 오류(최대 31일 등) |
| 429 | `잠시 후 다시 찾아 주세요` |
| 오프라인 | `연결이 필요합니다`. 마지막 결과를 보여 주지 않는다(만료 판단을 할 수 없음) |

- **금지:** `4/5명 가능`, 멤버 아바타, 누가 준비 안 됐는지, 몇 명이 준비 안 됐는지, 제외 원인(설계 6 §8, 설계 5 §10.2).

## 12. 제안 작성·응답·확정 (S16~S18, 체크리스트 7)

설계 7(`docs/proposal_lifecycle_design.md`) 구현과 함께 만든다.

### S16 제안 작성

```
┌───────────────────────────────┐
│ 취소       새 제안        보내기│
│ ┌───────────────────────────┐ │
│ │ ✦ 10월 30일 (목)          │ │  ← 결과에서 왔으면 고른 슬롯(고정)
│ │   오전 10:00 – 11:00 GMT+9│ │
│ └───────────────────────────┘ │
│ 제목                           │
│ ┌───────────────────────────┐ │
│ │ 저녁 산책                 │ │  1~80자
│ └───────────────────────────┘ │
│ 장소 (선택)                    │
│ ┌───────────────────────────┐ │
│ └───────────────────────────┘ │  최대 120자
│ 응답 마감   약속 시작 때까지 › │  ← 기본 start_at(설계 7 §4.2)
│ 받는 사람   멤버 4명 전원      │  ← 고를 수 없음, 안내만
│ 보내면 내 응답은 "수락"이에요. │
└───────────────────────────────┘
```

- 직접 시간 정하기(custom)에서 왔으면 슬롯 카드 자리에 날짜·시작·길이 선택(30분 단위, 30분~8시간)이 온다.
- 오류: `availability_result_stale` → `결과가 바뀌었습니다. 다시 찾아 주세요.`(S15로) / `proposal_time_conflict` → `이 시간에 겹치는 일정이 생겼습니다. 다른 시간을 골라 주세요.`(원인 비노출) / `calendar_sync_pending` → `그룹 준비를 기다리는 중`.
- 오프라인: 보내기는 큐에 넣을 수 있다(설계 7 §8). `보내는 중` 배지를 붙이고, 재연결 뒤 거부되면 사유를 보인다.

### S17 제안 상세·응답

```
┌───────────────────────────────┐
│ ‹ 주말 등산 모임               │
│ 저녁 산책                      │
│ 10월 31일 (금)                 │
│ 오후 7:00 – 8:00 GMT+9         │
│ 📍 한강공원 뚝섬               │
│ 응답 마감까지 1일 3시간         │
│ ┌───────────────────────────┐ │
│ │ 내 응답                    │ │
│ │ [ 수락 ] ( 미정 ) ( 거절 ) │ │  ← 세 버튼, 고른 것만 Primary
│ └───────────────────────────┘ │
│ 4명 중 2명 수락                │  ← 허용(설계 7 §9.1)
│ (민) 민지      ✓ 수락          │
│ (지) 지호      ✓ 수락 · 제안자 │
│ (서) 서연      ? 미정          │
│ (나) 나        … 응답 전       │
│ ───────────────────────────── │
│ 다시 제안하기 ›                │  ← 생성자·방장만
│ 제안 취소                      │  ← error, 생성자·방장만, 온라인만
└───────────────────────────────┘
```

| 상태 (설계 7 §8) | 상단 배너·표시 | 행동 |
|---|---|---|
| `open` | 남은 시간, 참여자별 응답 | 내 응답 바꾸기 |
| 가입 전 생성 | 정보 배너 `가입 전에 생성된 제안` | 응답 버튼 없음, 읽기 전용 |
| `awaiting_calendar_refresh` | 대기 배너 `캘린더 확인 중`. 2분 뒤에도 안 끝나면 내 캘린더가 원인일 때만 `( 내 캘린더 새로고침 )`, 아니면 `다른 멤버의 캘린더 확인을 기다리고 있습니다` | 응답 변경 가능(수락을 거두면 `open`으로) |
| `confirmed` | 성공 배너 `약속이 확정되었습니다` → S18로 | 확정 약속 보기 |
| `conflict_detected` | 경고 배너 `새로운 일정 충돌이 확인됨` | `다시 제안하기`(원인 비노출) |
| `reproposal_required` | 경고 배너 `참여자 구성이 변경됨` | `지금 멤버로 다시 제안하기` |
| `expired` | 중립 배너 `응답 기한이 지났습니다` | `다시 제안하기` |
| `cancelled` | 중립 배너 `제안이 취소되었습니다` | 없음 |
| `superseded` | 중립 배너 `새 제안으로 바뀌었습니다` | `새 제안 보기 ›` |
| `party_disbanded` | 문구 없이 Party 목록으로, 한 번 안내 | |

- 응답은 서버 성공 전에도 낙관적으로 보이되 `보내는 중` 배지를 붙인다. **확정은 서버 성공 전에는 보이지 않는다**(설계 7 §8).
- 오프라인 응답이 충돌하면 서버 상태를 먼저 보이고 `다른 변경이 먼저 반영됐습니다. 다시 골라 주세요.` 자동 덮어쓰지 않는다.
- 취소·다시 제안·확정 재시도는 온라인에서만. 오프라인이면 비활성 + `연결이 필요합니다`.
- 종단 상태 배너와 다시 제안 CTA에도 원인 사용자·충돌 일정·준비 안 된 사람 수를 쓰지 않는다.

### S18 확정 약속 상세

```
┌───────────────────────────────┐
│ ‹ 약속                         │
│ ✓ 확정                         │
│ 북한산 등산                    │
│ 11월 2일 (일) 오전 9:00 – 오후 1:00 GMT+9 │
│ 📍 북한산성 입구               │
│ 주말 등산 모임 · 4명           │
│ ┌───────────────────────────┐ │
│ │ ✓ 내 캘린더에 추가됨       │ │  ← 본인 반영 상태만(설계 8 §8.1)
│ └───────────────────────────┘ │
│ 참여자  (민)(지)(서)(나)       │  ← 반영 상태 열 없음
│ 새 시간 제안하기 ›             │  ← 재일정(설계 8)
│ 약속 취소                      │  ← error, 온라인만
└───────────────────────────────┘
```

- 본인 반영 배지: `반영 중` / `내 캘린더에 추가됨` / `조치 필요`(+ 설계 8 §8.2의 원인별 CTA) / `반영 대기 중 · 지정 기기에서 앱을 열어주세요`.
- 재일정 중이면 `새 시간 제안 중` 배지, 시각은 원래 그대로(설계 8 §8.4). 실패한 대체 제안 화면 안에는 새 제안 버튼을 두지 않는다.
- 취소된 약속은 취소한 사람 이름과 함께 `취소된 약속`으로 보인다(설계 8).

### S19 약속 목록 (권장 탭안)

```
┌───────────────────────────────┐
│ 약속                           │
│ 응답이 필요해요                │
│  저녁 산책 · 주말 등산 모임  › │
│ 다가오는 약속                  │
│  11월 2일 (일) 북한산 등산   › │
│    ✓ 내 캘린더에 추가됨        │
│ 진행 중인 제안                 │
│  스터디 정리 · 4명 중 3명 수락›│
│ 지난 약속 ›                    │
└───────────────────────────────┘
```

- 빈 상태: `아직 확정된 약속이 없습니다` + `[Party에서 시간 찾기]`(설계 8 §8.1.1). 캘린더 연결 상태는 말하지 않는다.
- 맨 위에 미해결 반영 문제(본인)가 있으면 경고 배너로 모은다(설계 9 §9.4).

## 16. 범위 확인이 필요한 화면

- **Party 일정(공유된 바쁜 시간) 보기:** 설계 5 §3이 "Party 일정 화면"의 표시 규칙(상세 공개·시간만 공개 projection)을 정의했지만, 체크리스트와 구현 계획에는 그 화면을 만드는 단계가 따로 보이지 않는다. 이 문서에는 넣지 않았다. 만든다면 멤버별 바쁜 시간이 보이는 화면이므로 hidden 멤버가 "일정이 없는 사람"처럼 보이지 않게 하는 설계가 따로 필요하다. 만들지 여부는 사용자 결정이다.
