# 백엔드 설계 우선순위 확정

## 확정 내용

- 서버 설계에서 초기 개발 속도보다 인프라 통제와 장기 확장성을 우선한다.
- 특정 BaaS의 데이터 모델에 앱을 직접 결합하지 않고 자체 API 경계를 둔다.
- 계정과 협업 도메인의 기준 데이터는 서버가 소유한다.
- 캘린더 반영과 알림은 재시도 가능한 비동기 작업 경계로 분리한다.

## 남은 결정

- 서버 언어·프레임워크
- API와 동기화 방식
- PostgreSQL 운영 방식
- 작업 큐·캐시 도입 시점
- 저장소 구성

## 다음 검증

- 공식 문서와 운영 특성을 기준으로 자체 백엔드 후보를 비교한다.
- 최종 기술 선택 이후 별도 검토 에이전트가 문서와 설계를 재검증한다.

## 후보 비교 결과

- 우선 권장안은 Go 자체 API, PostgreSQL 기준 데이터, PostgreSQL 기반 outbox/job, 필요 시 Valkey를 추가하는 구조다.
- API, worker, scheduler는 같은 코드와 컨테이너 이미지를 사용하되 프로세스 역할을 분리한다.
- 관리형 PostgreSQL과 컨테이너 실행 환경은 허용하지만 도메인 API와 데이터 모델은 자체 소유한다.
- Kubernetes, 마이크로서비스, 별도 메시지 브로커와 필수 캐시는 초기 범위에서 제외한다.
- 기술안은 사용자 확인 전까지 권장안 상태로 유지한다.
