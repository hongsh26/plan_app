## 범위

| 포함 | 미룸 |
|---|---|
| `GET /v1/sync?cursor=&limit=` (settled horizon 증분) | `POST /v1/sync` (로컬 mutation 배치) |
| `GET /v1/sync/bootstrap` (snapshot + watermark) | 정리 작업을 scheduler에 연결 (`Prune` 함수는 있다) |
| 정리 워터마크와 `Prune` 함수 (00004) | `notification_ref_key` 회전 |
| `notification_ref_key` 발급, bootstrap과 `/v1/me`에 싣기 (00003) | iOS 쪽(SwiftData App Group 이전 등) |
| mutation의 sync 변경을 전체 투영으로 변경 | |
| §15 순서 역전 회귀 테스트 | |

**`POST /v1/sync`를 미룬 이유.** 배치는 한 본문에 여러 idempotency 키를 담으므로 helper를 모든 도메인의
mutation 모양과 묶는다. 지금은 mutation이 3개뿐이고 클라이언트가 개별 endpoint를 부르면 된다.
도메인이 늘면 다시 쓰게 된다.

**`notification_ref_key`를 지금 넣은 이유.** 설계 9 §17.2가 설계 2의 bootstrap·`/v1/me` 응답에 이 필드를
추가하도록 개정했다. 응답 계약을 먼저 채워 두면 알림 구현 때 이미 배포된 응답을 바꾸지 않아도 된다.
00001에 `devices` 알림 열을 미리 넣은 것과 같은 판단이다.

## 확정한 방향

### 읽기: horizon을 같은 문장에서

`horizon = pg_snapshot_xmin(pg_current_snapshot())`, 세대, 정리 워터마크 비교, 변경 조회를 **한 SQL
문장**에서 한다. 따로 구하면 문장 사이에 snapshot이 달라진다. `LEFT JOIN LATERAL`로 변경이 없어도
첫 줄은 받는다. `limit + 1`로 읽어 `has_more`를 판단한다.

- 페이지가 잘렸으면 cursor는 마지막으로 전달한 위치다. 한 트랜잭션의 변경이 페이지 경계에서 갈라져도
  안전하다. 그 트랜잭션은 horizon 아래라 이미 끝났다.
- 다 받았으면 cursor를 `max(입력, 마지막 전달 위치, (horizon, -1))`로 당긴다. horizon 미만
  트랜잭션은 모두 끝났으므로 앞으로의 변경은 전부 `txid >= horizon`이다.
- `recipient_user_id = $1`이 권한의 전부이고 쿼리 안에 있다.
- `EXPLAIN`: `sync_changes_recipient_cursor_idx` 하나로 recipient, `(txid, ordinal)` 행 비교, horizon을
  모두 인덱스 조건으로 처리할 수 있다(`enable_seqscan=off`로 확인). 지금은 테이블이 작아 플래너가
  순차 스캔을 고른다.

### bootstrap: 한 snapshot, 최소 한 번 전달

REPEATABLE READ READ ONLY 트랜잭션의 **첫 문장**에서 horizon과 세대를 읽는다. 첫 문장이 트랜잭션
snapshot을 정하므로, 이후 읽는 사용자·기기와 같은 순간을 가리킨다. watermark는 `(horizon, -1)`이다.

**보장은 "정확히 한 번"이 아니라 "최소 한 번 전달 + version 비교로 한 번 적용"이다.** horizon 이상이지만
snapshot 시점에 이미 커밋된 트랜잭션의 변경은 snapshot에도 있고 증분으로도 다시 온다. `(txid, ordinal)`
순서 키만으로는 이 중복을 없앨 수 없다. 설계 §7.2 원문은 "다시 받지 않으면서"라고 적었는데, 이것은
구현할 수 없는 약속이어서 개정했다.

`notification_ref_key` 발급은 이 트랜잭션 **밖**에서 한다. 동시 첫 생성 경쟁을 `INSERT ... ON CONFLICT
DO NOTHING` 뒤 별도 문장 재조회로 해소하는데, REPEATABLE READ 안에서는 상대가 커밋한 row가 보이지
않는다. 같은 이유로 INSERT와 SELECT를 한 CTE로 합치지 않았다.

### sync payload는 전체 투영이다 (설계 §7.1 개정)

처음에는 mutation마다 바뀐 필드만 실었다(`{display_name}`, `{revoked: true}`). 리뷰 지적: 병합 규칙이
어디에도 정의되지 않았고, bootstrap이 폐기된 기기를 빼므로 watermark 이후에 폐기 upsert가 다시 오면
클라이언트는 로컬에 없는 entity의 한 필드짜리 payload를 받는다.

`account/projection.go`에 entity별 전체 투영(`UserProjection`, `DeviceProjection`,
`LiveDeviceProjections`)을 두고, mutation과 bootstrap이 모두 이것을 부른다. 클라이언트는 version이 더 큰
upsert를 받으면 payload로 통째로 바꾼다. 필드를 더할 때는 이 파일만 고친다.

### 410: 시각이 아니라 위치로 (설계 §7.1 개정)

처음 구현은 cursor에 발급 시각을 넣고 29일이 지나면 410으로 했다. 근거는 "정리는 created_at < 30일만
지우고, 어떤 트랜잭션도 하루 넘게 열려 있지 않다"였다. 리뷰 지적은 이렇다.

- 두 번째 조건을 강제하는 설정이 없다. 제가 적은 `idle_in_transaction_session_timeout`과
  `statement_timeout`은 한 문장과 유휴 구간만 제한하고 트랜잭션 전체 길이를 제한하지 않는다.
- 이틀 동안 쓰기 없이 열린 트랜잭션은 txid가 없어 horizon을 잡지 않는다. 그러다 쓰면 created_at이 이틀
  전인 row가 생긴다. 정리가 그것을 지워도 29일 cursor는 모른다.

**채택: 정리 워터마크.** `Prune`은 지운 row 중 가장 뒤의 `(txid, ordinal)`을 같은 트랜잭션에서
`sync_prune_state`에 기록한다. 읽기는 같은 문장에서 `cursor <= 워터마크`이면 410이다. 가정이 없다.
워터마크 뒤의 cursor는 지워진 row를 하나도 건너뛰지 않았다. 워터마크 이하는 건너뛰었을 수 있으므로
거부한다(보수적). 워터마크는 내려가지 않는다. cursor에서 발급 시각은 뺐다.

### cursor에 클러스터 세대

리뷰 지적: 비동기 복제본으로 장애 전환하거나 시점 복구하면 새 primary의 다음 txid가 클라이언트
cursor보다 작아질 수 있다. 그러면 이후 변경이 전부 cursor 앞에 쓰여 오류 없이 영원히 전달되지 않는다.

cursor에 `pg_control_system().system_identifier`와 `pg_control_checkpoint().timeline_id`를 담고, 다르면
410이다. api 역할로 두 함수를 읽을 수 있음을 확인했다. **남는 위험:** 같은 timeline 안에서 파일시스템
스냅샷으로 되돌리면 둘 다 그대로다. 그런 복구 뒤에는 운영 절차로 전체 재동기화를 강제해야 한다.
sync 읽기는 primary에서 한다.

cursor는 서명하지 않는다. 위조해도 `recipient_user_id`로 범위가 제한되어 자기 변경을 건너뛰는 것뿐이다.
아직 클라이언트에 발급한 적이 없어 형식을 자유롭게 바꿀 수 있었다. 앞으로는 버전 필드로 구분한다.

### 디렉터리 이름

§13은 `internal/sync/`이지만 `internal/syncfeed/`로 뒀다. 표준 라이브러리 `sync`와 패키지 이름이
같아지면 그 패키지 안에서 `sync.Mutex`를 쓸 때마다 별칭이 필요하다.

## 검증

- **§15 순서 역전 회귀 테스트**(`TestReadWithholdsChangesBehindInFlightTransaction`): 실제 별도 연결로
  A를 쓰고 커밋하지 않은 채 B를 커밋한다. 이때 B가 전달되지 않아야 하고, A 커밋 뒤 A, B가 순서대로 한
  번씩 와야 한다. **horizon 조건을 지우면 3회 모두 실패**한다("B가 먼저 전달됐다").
  P0부터 `progressing.md`에 빚으로 남아 있던 항목이 닫혔다.
- `TestBootstrapWatermarkKeepsInFlightChanges`: bootstrap 중 진행 중이던 트랜잭션의 변경이 이후 전달된다.
- `TestReadRejectsCursorAtOrBeforePruneWatermark`: 워터마크 판정을 지우면 실패한다.
- `TestReadRejectsCursorFromAnotherEpoch`: 세대 판정을 지우면 실패한다.
- 페이지 분할, 다른 사용자 변경 차단, cursor 역행 없음, 참조 키 동시 첫 생성, 전체 투영, HTTP 오류 코드

## 독립 리뷰 (code-reviewer, opus)

Critical·High 없음. Medium 3건(장애 전환 뒤 조용한 유실, 410 시간 가정 미강제, 부분 payload)은 위와
같이 고쳤다. Low 중 반영한 것: bootstrap에서 사용자 row가 없으면 500 대신 401, 테스트 공백(bootstrap 중
진행 중 트랜잭션, `/v1/me` 키 일관성), 설계 문서 §7.1·§7.2 개정. 남긴 것:

| 지적 | 처리 |
|---|---|
| PATCH 커밋 뒤 참조 키 발급이 실패하면 500 | **남김.** 같은 키로 재시도하면 재전송으로 정상 응답을 받는다 |
| `/v1/me` ETag가 user.version만 반영해 키 회전 뒤에도 같다 | **회전 구현 때.** 지금은 회전이 없다 |
| 2PC 잔여 트랜잭션이나 긴 쓰기 트랜잭션이 전 사용자의 sync를 멈춘다 | **의도.** 정확성의 대가다. §12의 sync horizon lag 경보(p95 5초, 30초 초과 경보)로 감시한다 |
| cursor의 horizon 대 앱 서버 시계 | 발급 시각을 빼면서 사라졌다 |
