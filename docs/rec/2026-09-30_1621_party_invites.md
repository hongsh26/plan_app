# Party P3 초대 API 구현

기준: `docs/party_membership_design.md` §4.2, §5.4, §5.5 T2·T3, §6, §8.3, §9.1, §9.3, §9.4, §10.
브랜치 `feature/party-invites`, 커밋 전.

## 구현

| Endpoint | 동작 |
|---|---|
| `POST /v1/parties/{id}/invites` | T2. 방장만. 기본 만료 7일, 기본 `max_uses = max(1, min(남은 정원, 10))`. 요청으로 `expires_in_seconds`(1시간~30일), `max_uses`(1~10) 지정. token은 생성 응답에만 |
| `GET /v1/parties/{id}/invites` | 방장만. `status='active' AND expires_at > now()`인 초대. token 없음 |
| `DELETE /v1/parties/{id}/invites/{invite_id}` | 방장만. 활성 초대를 `revoked`로, 방장에게 sync tombstone. 이미 끝난 초대는 현재 값을 돌려준다 |
| `GET /v1/invites/{token}/preview` | Party 이름, 활성 멤버 수, 초대자 표시 이름만 |
| `POST /v1/invites/{token}/accept` | T3 1~14단계 전부 |

- 코드: `server/internal/party/invites.go`, `projection.go`(`InviteProjection`), `party.go`(라우트·오류 매핑)
- 오류: `party_full`, `already_member`, `party_invite_limit_reached`(409), `rate_limited`(429), 만료·무효·소진·해산·미존재 모두 같은 `404 not_found`(메시지까지 동일)
- 잠금 순서: `users`(FOR NO KEY UPDATE) → `parties` → `party_invites`. users를 먼저 잡는 것은 같은 사용자의 서로 다른 Party 동시 수락이 참여 한도 20을 함께 넘지 못하게 직렬화하기 위해서다. T1과 같은 순서다
- sync: 신규 멤버에게 party + 모든 활성 멤버십 + 본인 공개 설정, 기존 멤버에게 party + 신규 멤버십, 방장에게만 `party_invite` upsert. outbox `notify_member_joined`(dedupe `membership_id`, payload는 식별자만)

## 설계와 다르게 한 결정

1. **재전송 시 token 원문 미반환.** `mutation`은 응답 본문이 아닌 결과 포인터만 저장하고(§8) DB에는 hash만 있으므로 원문을 복원할 수 없다. 같은 `Idempotency-Key` 재전송은 `201`과 `Idempotent-Replayed: true`, 초대 메타데이터를 돌려주되 `token`은 없다. 원문을 저장하면 §4.2·§7.4를 깬다. 응답을 잃은 클라이언트는 초대를 무효화하고 새로 만든다. 활성 초대 한도 3에는 여유가 있다
2. **sync 초대 version = `used_count + 1`.** `party_invites`에 version 열이 없고(migration 00010이 의도적으로 뺐다) sync upsert는 `entity_version`이 필요하다. upsert는 생성(0회)과 수락(정확히 +1)뿐이라 단조 증가한다
3. **생성 제한(시간당 10회)은 `party_invites.created_at` 카운트.** 무효화된 초대도 센다. 새 테이블 없음. 수락·미리보기 제한은 아래 제외 항목
4. 초대 생성·무효화는 `If-Match`를 받지 않는다. §4.4가 expected_version을 요구하는 mutation 목록에 초대가 없다

## 이번에 제외

- 수락 사용자당 분당 5회·IP당 30회, 미리보기 사용자당 분당 10회·IP당 30회 (§10 "미리보기가 분당 10회를 넘으면 429" 인수 조건 포함). 공용 rate limit 인프라가 없어 인증 rate limit(progressing.md "아직 남은 것")과 함께 설계한다
- Universal Link AASA 호스팅과 웹 폴백 페이지
- `calendar_busy_facts`가 없어 가입 시 projection은 기존 stub 그대로 0건
- `notify_member_joined` worker kind. 알 수 없는 type은 claim되지 않아 pending으로 쌓인다(설계 9 이후)

## 검증

실제 PostgreSQL(`REQUIRE_DB_TESTS=1`)로 `gofmt`, `go vet ./...`, `go test ./...` 통과, party 패키지는 `-count=3` 반복 통과. 테스트는 `invites_test.go`.

- token 256-bit(43자), DB에는 SHA-256만, row·sync·outbox·로그에 원문 없음, 목록에 원문 없음
- 활성 초대 4개째 409, 시간당 10회 429, 요청 검증 400, 방장 외 403/404
- 만료(scheduler 미실행, 저장 status=active)·소진·무효화·미존재·과도하게 긴 token·해산된 Party의 초대가 같은 404 본문
- 수락 정상 경로: 멤버십, `busyOnly` 설정, `used_count`, `invite_id`, sync 건수, outbox dedupe
- `already_member` 409에서 `used_count` 불변, 같은 키 재전송, 떠난 뒤 재전송은 404
- 정원 10 초과 409, 정원 찬 Party 초대 생성 409, 강퇴로 자리가 나면 수락 성공, 참여 20개 한도 409
- 마지막 자리 동시 수락: 1건 성공·1건 `party_full`, `mutation.Retries()` 증가 0

## 알게 된 것

- `disbandParty` 테스트 헬퍼는 활성 초대를 revoke하지 않는다. 실제 T7은 step 6에서 revoke하며, 지연 트리거가 "해산된 Party에 활성 초대 잔존"을 거부한다. 해산 후 남는 초대는 `exhausted`·`expired`·`revoked`뿐이다.
- `cleanupUser`는 `party_memberships.invite_id` FK 때문에 초대 삭제 전에 `invite_id`를 NULL로 만들어야 한다.
- 다른 셸 호출에는 DB 환경 변수가 이어지지 않는다. 변수 없이 돌린 `go test`는 통합 테스트를 전부 skip하고 `ok`를 출력한다.
