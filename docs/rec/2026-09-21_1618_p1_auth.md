## 범위를 어디서 끊었나

구현 계획 3·4단계는 인증, `/v1/me`, 기기 관리, 계정 삭제 상태 전이까지 담는다. 이번에는
그중 **idempotency와 무관한 것만** 했다. 기준은 스키마에서 나온다.

`idempotency_keys`는 `user_id`와 `device_id`를 NOT NULL FK로 요구하고, §6은 device ID를
access token claim에서 가져오라고 한다. 그래서 인증 endpoint는 구조적으로 idempotency 표에
들어갈 수 없다. 로그인 요청 시점에는 두 값이 아직 없거나(가입), 신뢰할 access token이 없다.
로그인의 중복 방지는 `auth_identities_provider_subject_key`와 Apple code의 1회성이 맡는다.
refresh의 중복 방지는 회전 자체가 맡는다.

반대로 `PATCH/DELETE /v1/me`, `DELETE /v1/devices/{id}`, `PUT .../push-token`은
Idempotency-Key와 expected_version이 필요한 mutation이다. mutation transaction helper(계획
5단계)보다 먼저 만들면 helper가 들어올 때 다시 써야 한다. **이것은 누락이 아니라 결정이다.**

| 포함 | 미룸 |
|---|---|
| `POST /v1/auth/apple`, `/refresh`, `/logout` | `PATCH /v1/me`, `DELETE /v1/me`(계정 삭제 요청) |
| 인증 미들웨어(매 요청 기기·계정 상태 DB 확인) | `DELETE /v1/devices/{id}`, `PUT /v1/devices/{id}/push-token` |
| `GET /v1/me`, `GET /v1/devices` | 인증 rate limit (§11) |
| L-6 `request_id` 미들웨어, §6 오류 응답 형식 | KMS envelope encryption |
| DB 역할 분리 자동 테스트 | OpenAPI 스키마 대 실제 응답 자동 대조 (§15 API 계약 테스트) |
| L-4 README Go 버전 표기 | |

## 확정한 방향

### Apple 상호작용은 한 경계에 모은다

identity token 검증, code 교환, revoke를 `internal/platform/appleid`에 두고 `auth`는 소비자
쪽 interface(`AppleVerifier`, `AppleCodeExchanger`)만 본다. P0 리뷰 L-5(interface는 소비자 쪽에)를
처음부터 따랐다. Apple 자격(.p8)이 로컬에 없어도 가짜로 모든 경로를 테스트할 수 있다.

### Apple 계약은 공식 문서로 다시 확인했다 (2026-09-21)

기억으로 고정하지 않았다. document-specialist가 developer.apple.com에서 확인한 것:

- JWKS `GET https://appleid.apple.com/auth/keys`. Apple은 **캐시 TTL이나 키 교체 주기를
  문서화하지 않는다.**
  (https://developer.apple.com/documentation/signinwithapplerestapi/fetch-apple-s-public-key-for-verifying-token-signature)
- identity token: `iss=https://appleid.apple.com`, `aud=client_id`, RS256. `email_verified`와
  `is_private_email`은 문자열과 bool이 **둘 다 올 수 있다.** 그래서 쓰지 않는 claim은 필드로
  받지 않는다. 받으면 타입이 바뀌는 순간 로그인 전체가 막힌다.
  (https://developer.apple.com/documentation/signinwithapple/verifying-a-user)
- token endpoint `POST /auth/token`: form 인코딩. 네이티브 앱은 `redirect_uri`가 필요 없다.
  authorization code는 1회용이고 5분 유효하다. 오류 `error` 값은 6개로 고정돼 있다.
  (https://developer.apple.com/documentation/signinwithapplerestapi/generate-and-validate-tokens)
- client secret: ES256, `kid` 헤더, `iss=team ID`, `sub=client_id`, `aud=https://appleid.apple.com`.
  최대 수명은 15777000초다.
- revoke `POST /auth/revoke`: 성공하면 200이고 본문이 없다.

실측: 2026-09-21에 운영 JWKS를 이 코드의 파서로 받아 RSA 키 3개(kid 10자)를 읽었다.

### JWKS 캐시 정책 (Apple이 정하지 않았으므로 우리가 정함)

- **24시간이 지난 키 집합**은 쓰기 전에 다시 받는다. 다시 받기에 실패하면 **낡은 키로 검증하지
  않고 거부**(503)한다. 낡은 키를 무기한 쓰면 폐기된 키로 서명한 token을 계속 받아들인다.
- **모르는 kid**가 오면 키 교체로 보고 다시 받는다.
- 두 경우 모두 **마지막 시도 후 1분 안에는 다시 받지 않고 즉시 실패**한다. 처음에는 만료
  경로에 이 제한이 없었다. 그래서 Apple 장애 중에 모든 로그인이 락 뒤에 줄을 서서 각자 timeout을
  기다린다는 리뷰 지적이 있었다. 임의 kid로 Apple을 두드리게 만드는 경로도 같이 막는다.
- 받기는 호출자 context와 분리하고 5초 한도를 둔다. 클라이언트가 연결을 끊어 받기가 취소되면
  그 실패가 1분 간격에 걸려 다른 사용자의 로그인까지 막히기 때문이다.
- `exp`·`iat` 판정에 30초 허용 오차를 둔다. 서버 시계가 조금 늦으면 방금 발급된 token의
  iat가 미래로 보인다.

### nonce는 필수다

iOS는 raw nonce의 SHA-256 hex를 Apple 요청에 싣고, 서버에는 raw nonce를 보낸다. 서버는
해시해서 token claim과 비교한다. nonce가 없는 로그인은 받지 않는다. 선택으로 두면 가로챈
token의 재사용을 막는 장치가 조용히 꺼진다.

### Apple refresh token 암호화: 로컬 전용 구현만, 배포 환경은 기동 거부

§11은 KMS envelope encryption을 요구하지만 KMS가 없다. 선택지는 셋이었다.

1. 평문 저장 → §11 위반. 탈락
2. 로컬 키 암호화를 모든 환경에서 쓴다 → 스테이징·프로덕션에서 키가 환경 변수에 평문으로
   놓인 채 "암호화됐다"고 믿게 된다. 탈락
3. **로컬 AES-GCM(`secretbox.NewLocal`)은 `APP_ENV=local`에서만 만들어지고, `config.LoadAuth`는
   local이 아니면 api 기동을 거부한다.** 채택

그 결과 **KMS 구현 전까지 api는 스테이징·프로덕션에 배포할 수 없다.** 의도한 제약이다.

Apple code 교환 자격이 없으면 로컬에서는 교환을 건너뛴다. 그러면 Apple refresh token이 없는
계정이 생기므로 기동 로그에 경고를 남긴다. 교환 자격은 세 변수가 모두 있거나 모두 없어야
한다. 일부만 있으면 오타로 보고 거부한다.

**code 교환이 Apple에 거부되면 로그인도 실패시킨다.** 교환 없이 가입시키면 §10 3단계에서
revoke할 token이 없는 계정이 남는다. 단, 사용자 탓인 거부(`invalid_grant`)만 401로 답한다.
`invalid_client` 같은 나머지는 서버 자격 문제다. 401로 답하면 .p8 키가 만료됐을 때 모든 로그인이
"다시 로그인하라"로 보이고 운영자는 원인을 모른다. 그래서 500을 내고 Apple error code를 로그에
남긴다.

**code 교환 응답의 `id_token` sub가 검증한 identity token의 sub와 같아야 한다.** code와 identity
token은 따로 제출되므로, 확인하지 않으면 남의 code를 자기 token과 함께 내서 남의 Apple grant를
내 계정에 저장시킬 수 있다. 응답의 `id_token`은 Apple token endpoint가 TLS로 직접 준 것이라
서명을 다시 검증하지 않고 sub만 읽는다.

### 세션

- access token: HS256, 15분, `sub`=user_id, `did`=device_id, iss·aud 고정. kid 교체는
  아직 없다. 키를 바꾸면 발급된 token이 전부 무효가 되지만, 사용자는 refresh 한 번만 겪는다.
- refresh token: `rt_` + 256-bit 난수. DB에는 SHA-256만 저장한다. 난수라 느린 해시가 필요
  없고, 조회 키로 쓰려면 결정적이어야 한다. 30일이고 회전할 때마다 30일로 다시 늘어난다.
- **로그인할 때마다 서버가 새 device ID를 발급한다.** 클라이언트는 device ID를 증명할 수
  없으므로 재사용하지 않는다.
- **로그아웃과 refresh 재사용 탐지는 기기 자체를 폐기한다.** 세션만 폐기하면 이미 발급된
  access token이 최대 15분 더 쓰인다. token family는 기기 하나 안에서만 생기므로 기기 폐기가
  family 전체 폐기를 포함한다.
- **인증 미들웨어는 매 요청마다 기기 폐기와 계정 상태를 DB에서 확인한다.** §14 "잠긴 계정은
  보호 API를 쓸 수 없다"와 §5.2 "즉시 폐기"는 서명된 token만으로는 지킬 수 없다. 대가는
  요청당 PK 조회 1회다.
- **refresh 재사용 탐지는 엄격하다.** 응답을 잃은 정상 클라이언트가 같은 token으로 재시도해도
  재사용으로 판정되어 다시 로그인해야 한다. §5.2가 요구하는 동작이고, 유예 창을 두는 완화는
  하지 않았다.

### 잠금과 경쟁

- 최초 로그인이 동시에 오면 `ON CONFLICT (provider, provider_subject) DO NOTHING`에서 진
  쪽이 트랜잭션을 버리고 다시 시도해 이긴 쪽의 계정을 찾는다. 8개 동시 요청으로 계정이
  1개인지 테스트한다.
- **잠금 순서는 모든 인증 경로에서 `users`(FOR SHARE) → `devices`(FOR UPDATE) → `sessions`다.**
  처음에는 refresh가 세션 row를 먼저 잠갔고, 같은 기기의 로그아웃과 교착(40P01)할 수 있다는
  리뷰 지적이 있었다. 로그아웃의 잠금을 빼면 테스트가 교착을 실제로 재현한다.
  refresh는 세션의 소유자를 잠금 없이 먼저 읽고, 순서대로 잠근 뒤 다시 읽는다.
- **계정 삭제를 구현할 때 이 순서를 따라야 한다.** `users`를 FOR UPDATE로 잡고, 이어서
  기기와 세션을 폐기한다. 상태 변경과 세션 전체 폐기를 한 트랜잭션에서 해야 로그인의
  `FOR SHARE`와 맞물려 "삭제된 계정에 살아 있는 세션이 없다"가 성립한다.
- 같은 refresh token으로 동시에 요청하면 **정확히 하나**만 성공한다. 테스트로 확인한다.

### 로그

- `request_id`는 서버가 발급한다. 클라이언트의 `X-Request-ID`는 채택하지 않는다. 채택하면
  다른 요청의 ID를 재사용해 audit 상관관계를 오염시킬 수 있다.
- access log의 action은 원본 경로가 아니라 **ServeMux가 매칭한 route 패턴**이다. 원본
  경로·query에는 기기 ID와 sync cursor가 섞인다. 매칭되지 않은 요청은 `unmatched`로 남긴다.
- 예상하지 못한 오류는 원문 대신 **분류만** 남긴다(PostgreSQL은 SQLSTATE, 그 밖은 Go 타입).
  원문에는 SQL, 값, 연결 정보가 섞일 수 있다.

### 테스트가 실제로 잡는지 확인한 것 (mutation)

- `plantogether_api`의 users INSERT를 회수 → `TestRuntimeRolesCanReadAndWriteDomainTables` 실패
- `plantogether_readonly`에 DELETE 부여 → `TestReadonlyRoleCannotWrite` 실패
- `WithIssuer` 제거 → "다른 issuer" 케이스 실패. `WithIssuedAt` 제거 → "미래의 iat" 케이스 실패
- `WithValidMethods` 제거 → **테스트는 통과한다.** golang-jwt의 HS256 검증기가
  `*rsa.PublicKey`를 키로 받지 않아 알고리즘 혼동이 이중으로 막히기 때문이다. 두 겹 모두
  유지하고 테스트 주석에 적었다.
- 로그아웃의 `lockUserAndDevice` 제거 → `TestConcurrentRefreshAndLogoutDoNotDeadlock`이
  `deadlock detected (SQLSTATE 40P01)`로 실패(5회 반복 중 재현)
- 개발 중 테스트가 실제 버그를 하나 잡았다. 로그인 결과의 `NewUser`가 세션 발급 결과를
  대입하면서 덮어써져 항상 false였다.

| 지적 | 처리 |
|---|---|
| `sessions`가 회전마다 row를 남겨 무한히 는다(기기당 하루 최대 96행) | **남김.** 재사용 탐지에 쓰인 row(`used_at`)가 필요하다. 만료·폐기된 row의 정리는 scheduler 작업으로 한다 |

| 잠긴 계정도 Apple code를 먼저 교환하고 받은 grant를 버린다 | **남김.** 상태는 DB 트랜잭션 안에서만 확정되고, 외부 호출 동안 행 잠금을 쥐지 않으려고 교환을 트랜잭션 밖에 뒀다 |
| 재로그인마다 Apple refresh token 암호문을 덮어써 이전 grant가 revoke되지 않는다 | **남김.** Apple은 같은 앱의 grant를 사용자당 하나로 관리하므로 영향이 작다. 계정 삭제 구현 때 다시 본다 |
| 인증 없는 로그인 실패마다 `audit_events`가 쌓인다 | **남김.** 인증 rate limit과 함께 다룬다 |
| access log의 `status`는 §11 허용 목록 밖이다 | **유지.** result의 세부 값으로 해석하고 주석에 적었다. 401·423·503을 구분하지 못하면 장애 대응이 불가능하다 |
| api가 복호화 가능한 대칭 키를 가진다(§11 "api 역할은 복호화 권한 없음" 위반) | **KMS 구현 때 해결.** api는 암호화 권한만, 삭제 worker만 복호화 권한을 갖게 한다. 로컬 구현은 local 전용이라 지금은 영향이 없다 |
| `FOR SHARE OF u` 제거를 잡는 테스트가 없다 | **남김.** 상태 변경과 로그인의 동시성 테스트는 계정 삭제 구현 때 삭제 경로와 함께 만든다 |
