## 왜 이 세 건만 골랐나

P0 서버 골격은 `ccc0b1b`에서 완료 기준(마이그레이션 적용, liveness·readiness
응답)을 만족했고 독립 리뷰에서 Critical·High가 없었다. 남은 것은 Medium 3건과
Low 6건이었다. `main` 병합 전에 닫을 것과 P1로 넘길 것을 나눈 기준은
**"병합 후에 이것이 없으면 이후 작업이 잘못된 신호 위에 쌓이는가"** 하나다.

- **M-5**는 파괴적 연산에 가드가 없다. 막지 않고 병합하면 가드 없는 `DROP`
  경로가 `main`에 들어간다.
- **M-8**은 `REQUIRE_DB_TESTS=1`을 켜는 주체가 없다. CI 없이 병합하면 통합
  테스트가 skip된 채로 `main`이 초록불을 유지하고, 이후 모든 병합의 초록불이
  같은 이유로 신뢰할 수 없게 된다.
- **M-9**는 M-8이 켜준 게이트가 실제로 무엇을 검사하는지의 문제다. M-8과 한 쌍
  이므로 함께 닫는다.

L-1~L-6은 병합을 막지 않으므로 P1로 넘긴다. L-6(`request_id` 미들웨어)은 이미
P1 인증 작업으로 스코프돼 있었다.

## M-5 — 파괴적 마이그레이션 가드

### 문제

`-migrate reset`이 `APP_ENV`를 보지 않았다. 프로덕션 api task에
`MIGRATION_DATABASE_URL`이 주입돼 있으면 `-migrate reset` 한 번으로 8개 테이블이
전부 `DROP`된다.

### 결정 1: `down`도 막는다 (리뷰 지적의 문자 범위를 넘는 판단)

리뷰는 `reset`만 지목했다. 그러나 현재 마이그레이션은 `00001_init.sql` 하나뿐
이라 `goose.DownContext`(`down`)와 `goose.DownToContext(..., 0)`(`reset`)이
**같은 결과**를 낸다. 둘 다 8개 테이블을 전부 `DROP`한다. `reset`만 막으면
가드는 이름만 남고 실제로는 `down`으로 그대로 뚫린다.

마이그레이션이 늘어나 `down`의 폭이 한 단계로 줄어든 뒤에도 목록에 남긴다.
되돌리기는 운영 DB에서 사람이 판단할 일이지 프로세스 인자 하나로 실행될 일이
아니다.

`up`과 `status`는 막지 않는다. 막으면 프로덕션 배포의 `-migrate up`이 함께
죽는다. 이것은 회귀 테스트로 고정했다
(`TestMigrateAllowsNonDestructiveDirectionsInProduction`).

### 결정 2: 가드를 호출자가 아니라 `postgres.Migrate` 안에 둔다

`cmd/api/main.go`의 CLI 인자 검사로 두면, 앞으로 추가될 진입점이 그대로
빠뜨릴 수 있다. `DROP`을 실제로 수행하는 함수가 스스로 거부해야 우회 경로가
생기지 않는다. `Migrate`의 시그니처에 `env string`을 추가했다.

### 결정 3: 가드는 `sql.Open` **이전**에 판정한다

연결 이후에 판정하면 거부가 "DB에 닿을 때만" 성립하고, 닿지 않으면 연결 오류에
가려진다. 연결 전에 두면 실제 PostgreSQL 없이 가드를 단위 테스트할 수 있다.
이 순서 자체를 `TestMigrateGuardRunsBeforeOpeningConnection`이 고정한다.

### 결정 4: `APP_ENV`를 마이그레이션 경로에서도 필수로 만든다

기존 `LoadMigrationDatabaseURL`은 `MIGRATION_DATABASE_URL`만 읽었다. 환경을
모르면 파괴적 연산을 거부할지 판단할 수 없고, "모르면 허용"은 프로덕션 스키마를
날리는 쪽으로 실패한다. `LoadMigrationSettings`로 바꿔 `APP_ENV`를 함께 요구한다.

`APP_ENV` 허용 값(`local`/`staging`/`production`)은 `config.EnvLocal` 등 상수로
승격했다. 리터럴이 여러 패키지에 흩어지면 오타 하나로 가드가 조용히 무력화된다.

### 변경 파일

- `internal/platform/postgres/migrate.go` — `ErrDestructiveMigrationNotLocal`,
  `isDestructive`, `Migrate`에 `env` 인자
- `internal/platform/config/config.go` — `EnvLocal`·`EnvStaging`·`EnvProduction`
  상수, `MigrationSettings`, `LoadMigrationSettings`
  (`LoadMigrationDatabaseURL` 대체)
- `cmd/api/main.go` — 호출부와 `-migrate` 플래그 도움말
- `internal/platform/postgres/migrate_test.go` — 신규, DB 불필요
- `internal/platform/config/config_test.go` — `LoadMigrationSettings` 테스트

## M-9 — CHECK constraint 테스트가 SQLSTATE를 보지 않았다

### 문제

`TestStatusCheckConstraintsRejectUnknownValues`가 `err == nil`만 확인했다. 열
이름이 바뀌어 `undefined_column`(42703)이 나도, 타입 오류가 나도 `err != nil`
이므로 통과한다. 제약이 통째로 사라져도 초록불일 수 있다.

리뷰가 지목한 것은 이 테스트 하나지만, **`TestUserDeletedAtAllowsDeletionPipeline`
에도 같은 결함이 있었다** (`active`/`disabled`/`deletion_requested` 세 건의
`err == nil` 검사). 함께 고쳤다.

### 변경

기존 `assertUniqueViolation`과 같은 구조로 `assertCheckViolation`을 추가했다.
SQLSTATE `23514`와 제약 이름까지 확인한다. 기존 관용구를 그대로 따르는 것이
여기서는 개선보다 중요하다.

확인하는 제약 이름 4개:

- `users_status_check`
- `devices_push_authorization_check`
- `outbox_jobs_status_check`
- `users_deleted_at_requires_terminal_status_check`

## M-8 — CI

### 문제

`REQUIRE_DB_TESTS=1`을 켜는 주체가 저장소에 없었다. `.github` 디렉터리 자체가
없어 `go test ./...`가 통합 테스트 9건을 전부 skip하고 `ok`를 출력한다.

### 결정: GitHub Actions `services:`가 아니라 `docker compose`를 쓴다

`services:` 블록은 `docker-entrypoint-initdb.d`를 마운트할 수 없다. 그러면
`docker/postgres-init/01-roles.sql`을 별도 스텝으로 다시 적용해야 하는데,
`ALTER DEFAULT PRIVILEGES FOR ROLE plantogether_migration`은 마이그레이션보다
먼저 실행돼야 의미가 있어서 순서가 어긋나면 조용히 권한이 갈라진다. compose를
쓰면 고정된 `postgres:18.2-alpine` 태그와 같은 초기화 경로를 CI와 로컬이
공유한다.

`docker compose up -d --wait`으로 compose의 healthcheck(`pg_isready`) 통과를
기다린다. `sleep`으로 대체하면 연결 실패가 테스트 실패로 위장된다.

Go 버전은 `go-version-file: server/go.mod`로 읽는다. 워크플로에 버전을 적으면
`go.mod`와 갈라지는 세 번째 출처가 생긴다.

### skip 0건 확인 스텝에서 걸린 함정

처음에 `grep -c '"Action":"skip"'`으로 세려고 했으나, `go test -json`은 **테스트
파일이 없는 패키지**(`cmd/api`, `cmd/worker`, `cmd/scheduler`, `migrations`)에도
패키지 수준 `Action:"skip"`을 낸다. 그대로 두면 이 스텝이 항상 실패한다.
테스트 수준 skip에만 있는 `"Test":` 필드를 함께 걸어 구분했다.

이 스텝은 `REQUIRE_DB_TESTS=1`의 이중 안전장치다. 앞으로 `connect()` 헬퍼를
거치지 않는 테스트가 추가되면 `REQUIRE_DB_TESTS`만으로는 skip을 잡지 못한다.

### 워크플로가 확인하는 것

`gofmt` -> `go vet` -> DB 기동 -> `migrate up` -> `migrate status` ->
`go test -v` -> skip 0건 -> `reset`/`up` 왕복 -> `APP_ENV=production`에서
`reset` 거부.

마지막 스텝이 M-5의 가드가 **진입점까지 연결돼 있는지**를 확인한다. 단위
테스트는 `postgres` 패키지 안에서만 성립하고, `cmd/api`가 `env`를 실제로
넘기는지는 여기서만 드러난다.

## 실측 검증

로컬 PostgreSQL(`docker compose up -d --wait`, `postgres:18.2-alpine`)에서 CI
스텝을 그대로 실행했다.

| 항목 | 결과 |
|---|---|
| `gofmt -l .` | 출력 없음 |
| `go vet ./...` / `go build ./...` | 통과 |
| 전체 테스트 (`REQUIRE_DB_TESTS=1`) | 5개 패키지 `ok` |
| **M-5 가드 mutation 테스트** | `isDestructive`를 `return false`로 바꾸자 **10개 subtest 실패**. 복구 후 통과 |
| `APP_ENV=production` + `-migrate reset` | 거부 (`방향 reset, APP_ENV production`) |
| `APP_ENV=production` + `-migrate down` | 거부 |
| `APP_ENV` 미설정 + `-migrate reset` | 거부 (`APP_ENV가 설정되지 않았다`) |
| 거부 후 스키마 생존 | `migrate status`가 `00001_init.sql` 적용 상태 유지 |
| `APP_ENV=local` `reset` -> `up` 왕복 | 성공 |
| M-9 대상 테스트 2개 | 9개 subtest 전부 PASS (SQLSTATE 23514 + 제약 이름 일치) |
| **skip 감지 스텝 양방향** | DB 있음 + `REQUIRE_DB_TESTS=1`: skip 0건 통과 / DB URL 없음: **skip 9건 검출해 실패** |

마지막 줄이 M-8의 주장을 그대로 재현한다. 게이트가 없으면 통합 테스트 9건이
조용히 skip된다.

## 아직 검증되지 않은 것

**GitHub Actions에서 실제로 돌려본 적이 없다.** 위 검증은 워크플로의 각 스텝을
로컬에서 동등하게 실행한 것이다. 원격 push 후 첫 실행이 초록인지, 그리고
**일부러 테스트를 깨뜨렸을 때 빨간불이 나는지**를 확인해야 M-8이 실제로 닫힌다.
초록불 하나만으로는 "9건이 돌아서 통과"와 "9건이 skip돼서 통과"를 구분하지
못한다. 워크플로에 `-v`와 skip 0건 스텝을 둔 이유가 이것이고, 원격 확인은
병합 직후의 할 일로 남는다.

## 남은 리뷰 지적

L-1(로그의 DB 접속 정보), L-3(goose `StatementBegin/End` 분할),
L-4(README Go 버전 표기), L-5(`Pinger` interface 위치), L-6(`request_id`
미들웨어). 전부 P1 이후.

L-1과 관련해 이번에 하나 추가로 관찰했다. `migrate.go`의 연결 실패 경로가
pgx 오류를 `%w`로 감싸고 있어 오류 문구에 `user=...`와 `database=...`가 남는다
(가드 mutation 테스트 로그에서 드러났다). `postgres.go`의 `NewPool`은 같은
이유로 이미 원문을 버리고 있으므로 일관성이 어긋난다. L-1을 처리할 때 이
경로도 함께 본다.
