## Hangly 요약

- **문제 정의:** 친구를 만나고 싶은 마음은 있는데, 일정 맞추기·예산·흩어진 도구·단체 대화방 때문에 계획이 무너진다. 연구 대상(페르소나)은 결국 집에 남는다.
- **원칙 3가지:** Constraints first(시간·예산·가용성을 기능보다 먼저 받는다), Planning should feel quieter(결정과 단계를 줄인다), Inclusion by default(자기 한계를 설명하지 않아도 되게 한다).
- **화면:** 환영, 가입, 선호 설정, 친구 추가, 알림, 벤토 대시보드("Start a Hang" 큰 원형 버튼, 내 그룹, 메시지), 그룹 선택·생성(친구 체크박스), 장소 찾기(목록/지도 전환, 친구 이름이 찍힌 지도, "Show friend's availability" 토글), RSVP(장소 사진, 친구 사진 + 체크, "Confirmed 3/4", RSVP 카운트다운).
- **시각:** 연한 하늘색 배경, 코랄 빨강 강조, 세리프 제목, 실제 인물 사진, 그룹마다 이모지 아이콘.
- **검증에서 배운 점:** 초기 시제품이 처음에 너무 많은 것을 물었다. 단계를 줄이고 순서를 바꿔 대시보드에 빨리 닿게 했다.

## 취할 점

| 취할 점 | 우리 앱에서의 형태 | 이유 |
|---|---|---|
| "계획은 조용해야 한다" | 한 화면에 주된 행동 하나. Party 상세의 주 버튼은 `모두 가능한 시간 찾기` 하나다 | 설계 6·7의 흐름(검색 → 슬롯 선택 → 제안)이 원래 일직선이다. 단계 수를 늘리지 않는다 |
| 제약 먼저 (Constraints first) | 준비를 "캘린더 연결 → 활동 시간"으로 묶고, 검색했는데 본인 준비가 안 됐으면 그 자리에서 고치게 한다 | 설계 6 §8의 본인 CTA(`내 활동 시간 설정`, `내 캘린더 새로고침`)와 같은 방향이다 |
| 처음에 덜 묻기 | 가입은 이메일·비밀번호·표시 이름만. 캘린더·활동 시간은 로그인 뒤 "준비" 체크리스트로 안내한다. 알림 권한은 첫 Party 참여 뒤에 묻는다 | 설계 9 §9.1(첫 실행에 알림 권한을 묻지 않는다)과 맞는다 |
| 큰 주 행동 버튼 하나 | Party 목록 위쪽의 "다음 할 일" 카드, Party 상세의 큰 `모두 가능한 시간 찾기` 버튼 | 무엇을 눌러야 하는지 바로 안다. 다만 Hangly처럼 화면 가운데를 가리는 원형 버튼은 쓰지 않는다(큰 글자 크기에서 깨진다) |
| 그룹 카드에 "다음에 할 일" | Party 카드에 다음 확정 약속 또는 내 응답이 필요한 제안 하나를 보인다 | 벤토 대시보드의 "한곳에서 본다"를 가져오되 한 줄로 줄인다 |
| RSVP 카운트다운의 의도 | 제안 화면에 `응답 마감까지 1일 3시간`처럼 남은 시간을 문장으로 보인다 | 설계 7 §8 `open` 상태의 "남은 시간"과 같다. 초 단위 숫자 카운트다운은 압박이 크고 VoiceOver가 계속 읽어서 쓰지 않는다 |
| 제안 응답 요약 ("Confirmed 3/4") | 제안 화면에 `4명 중 2명 수락`과 참여자별 응답 목록 | **제안 응답은 설계 7 §8·§9.1이 활성 멤버 전원에게 공개하는 협업 데이터다.** 가능 시간 결과의 인원 표시와는 다르다(아래 버릴 점 첫 줄) |
| 그룹마다 다른 얼굴 | Party마다 아이콘 손 색 4가지 중 하나를 **Party ID로 기기가 계산해** 붙인다 | 새 서버 필드 없이 Party를 구별한다. Hangly의 그룹 이모지는 새 데이터 필드가 필요해서 가져오지 않는다 |

## 버릴 점

| 버릴 점 | 이유 |
|---|---|
| **"Show friend's availability" 토글과 친구 이름이 찍힌 가용성 지도** | 누가 되는지를 멤버별로 보여 준다. 설계 5 §10.2와 설계 6 §8은 결과에 인원·멤버·원인을 금지하고, 설계 3 §4는 "누가, 어떤 일정 때문에, 몇 명이"를 반환하지 않는다고 정했다. 우리는 전원 공통 슬롯만 보인다 |
| "가장 많은 사람이 되는 시간" 같은 부분 일치 | 결과는 전원 공통 슬롯뿐이다. 부분 일치는 설계 3 §4가 Post-MVP에서도 privacy review 전에는 금지한다 |
| 결과 화면의 멤버 사진·아바타 | 설계 6 §8 금지. 아바타는 멤버 목록과 제안 응답 목록에만 둔다 |
| 친구 위치 지도, 장소 찾기·추천, 장소 사진, 별점·거리 | 위치를 수집하지 않는다. 장소 추천은 Post-MVP(기능 목록 13번)다. 제안의 장소는 사용자가 쓴 글자(최대 120자)일 뿐이다 |
| 예산 입력과 예산 맞춤 추천 | 체크리스트 밖이다 |
| 연락처 동기화, 친구 추가, 친구 목록에서 그룹 만들기 | 친구 관계가 없고 초대 링크로만 들어온다(설계 4 §3.2). 연락처를 읽으면 개인정보 표면만 늘어난다 |
| 메시지·알림 피드(대시보드 안 대화) | 채팅은 범위 밖이고 앱 안 알림함도 만들지 않는다(설계 9 비목표) |
| "Suggested Hangs"(이벤트 추천) | 범위 밖. AI 추천은 Post-MVP다 |
| 햄버거 메뉴와 상단 종 아이콘 | iOS 표준 탭 바를 쓴다. 메뉴에 숨기면 찾기 어렵고, 알림함이 없으니 종을 눌러 갈 곳이 없다 |
| 실제 인물 사진 | 프로필 사진 필드가 없다. 표시 이름 첫 글자 모노그램만 쓴다 |
| 밝은 코랄 글자를 흰 바탕 제목·버튼 글자로 쓰기 | 밝은 코랄은 흰 바탕에서 본문 대비 4.5:1에 못 미친다. 우리는 코랄을 면과 장식에만 쓰고 글자에는 짙은 변형 토큰을 쓴다(`design_system.md` §2) |
| 세리프 제목 | 우리 톤은 아이콘의 둥글고 통통한 3D다. SF Pro Rounded가 맞는다 |
| RSVP 화면에서 `Cancel`이 주 버튼과 같은 무게로 나란히 있는 배치 | 파괴적 동작은 주 버튼과 떨어뜨리고 확인을 받는다(설계 4 §3.6, 설계 7 §4.4) |
