# 프로젝트 Goal과 End

프로젝트가 끝없이 늘어나지 않게 하는 문서다. **아래 체크리스트를 모두 충족하면 신규 기능 개발을 멈추고 프로젝트를 종료한다.** 확정일: 2026-10-28.

## Goal: Launch MVP

> 사용자가 Apple로 로그인하고 캘린더를 연결한 뒤 Party에 구성원을 초대하여 공개 범위를 설정하고, 모두 가능한 시간을 찾아 약속을 제안·확정한 다음 각자의 Apple Calendar에 반영하고 변경·취소 알림까지 받을 수 있다.

범위는 `docs/feature_design_backlog.md`의 "Launch MVP" 절과 같다.

**판정 기준:** 기능 항목(1~10)은 괄호 안 단계마다 `.omc/plans/` 계획의 완료 기준을 통과하고, 그 근거(테스트·rec 문서)가 있어야 체크한다. 해당하는 경우 서버와 iOS가 모두 끝나야 한다. 사용자 관점의 동작("세션 유지", "상태가 맞는다")은 14번 E2E가 최종 판정한다. P·V 단계 이름은 `party-membership-implementation.md`·`party-visibility-implementation.md`의 것이다.

## End 체크리스트

### 기능 (사용자 시나리오 순서)

- [ ] **1. 로그인·세션·프로필:** Apple 로그인, 세션 유지, refresh, 로그아웃, 프로필 수정. 서버 코드는 있지만 가짜 Apple 검증기로만 테스트했다. 실제 Apple 자격 검증과 iOS가 남았다
- [ ] **2. 동기화:** bootstrap과 증분 sync로 두 기기의 상태가 맞고, 오프라인 상태에서 재시도한다. `GET /v1/parties`도 포함한다 (P6)
- [ ] **3. 캘린더 연결:** Apple Calendar 권한, snapshot 업로드, freshness. 서버 C1~C5는 끝났고 iOS가 남았다
- [ ] **4. Party:** 생성, 초대 Universal Link, 수락, 위임, 탈퇴, 강퇴, 해산 (P1~P5, P9, P10). 서버 P1~P5는 끝났고 AASA 호스팅, P9, P10이 남았다
- [ ] **5. 공개 수준:** Party별 설정과 캐시 삭제 (V1~V6). 서버 V1~V3는 끝났다. V3 iOS, V4(A 단계와 함께), V5, V6가 남았다
- [ ] **6. 공통 시간 검색:** 활동 시간 설정, 전원 공통 슬롯 검색 (A0~A6)
- [ ] **7. 제안·응답·확정:** (Q0~Q7)
- [ ] **8. 캘린더 쓰기:** 확정 일정의 쓰기·변경·취소와 실패 복구 (W0~W8)
- [ ] **9. 알림:** 제안·확정·변경·취소 푸시 (N0~N8, P7과 `notify_*` worker kind 5종). 초대 푸시는 설계 9에 따라 없다
- [ ] **10. 계정 삭제:** 계정을 지우면 Party 강제 위임·해산까지 처리한다 (P8)

### 출시 조건

- [ ] **11. KMS 구현:** `APP_ENV=local`이 아닌 환경에서도 api가 기동한다
- [ ] **12. 배포와 요청 제한:** 스테이징 api가 `/readyz` 200을 반환한다. `CLIENT_IP_SOURCE`·`TRUSTED_PROXY_HOPS`·`RATE_LIMIT_KEY`를 설정하고, `client_ip_fallback`·`limiter_error` 로그에 경보를 건다. 공개 수준·검색·제안 endpoint가 `ratelimit.Enforce`를 호출한다
- [ ] **13. API 계약:** 모든 endpoint가 OpenAPI에 등재되고, 실제 응답과 자동으로 대조된다
- [ ] **14. E2E:** 위 필수 시나리오를 실제 기기 2대(또는 기기와 시뮬레이터)로 처음부터 끝까지 통과한 기록이 `docs/rec/`에 있다
- [ ] **15. 제출 준비:** TestFlight에 배포한다. 개인정보 처리방침을 `docs/privacy_policy.md`에 쓰고, App Store 개인정보 라벨 입력을 끝낸 기록을 `docs/rec/`에 남긴다

## 범위 규칙

- 체크리스트에 없는 기능은 만들지 않는다. 체크리스트 항목에 딸린 문서 갱신·rec 기록·재검증·테스트는 예외다. 새 아이디어는 `feature_design_backlog.md`의 Post-MVP에만 적는다.
- 체크리스트 항목을 추가·삭제·변경하려면 **사용자 승인**이 있어야 한다. 바꾸면 아래 변경 이력에 남긴다.
- 리뷰의 Low 지적은 출시를 막지 않는다. 남은 Low에는 P0 L-1·L-3·L-5, 로그인 동시성 테스트, Apple 오류 HTTP 계층 테스트가 있다. High·Medium만 해당 항목 안에서 처리한다.
- 시연(2·5·6번 우선)은 중간 이정표일 뿐 End가 아니다.

## End 절차

1. 15개 항목을 모두 체크한다. 그다음 서브 에이전트가 각 항목의 근거를 재검증한다
2. 기능 브랜치는 완성될 때마다 `main`에 병합한다(CLAUDE.md 규칙). 마지막에 남은 브랜치가 없는지 확인하고 릴리스 태그 `v1.0.0`을 단다
3. `docs/rec/`에 종료 기록을 남긴다. `progressing.md`는 "종료. 이후 작업은 Post-MVP로 새 Goal을 정할 때만 재개"로 바꾼다

## 변경 이력

- 2026-10-28: 최초 확정. Goal = Launch MVP, End = 체크리스트 전부 충족 시 종료
- 2026-10-28: 재검증 반영. 판정 기준을 명시하고, 1번 상태를 바로잡았다. 프로필·오프라인 재시도·P10·요청 제한 소비자를 넣고, 12·15번에 증거 기준을 정했다
