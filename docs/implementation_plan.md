# 그룹 일정 관리 앱 작업 계획

## 기준과 현재 상태

- 기준 문서: `docs/group_calendar_mvp_design.md`.
- 현재 저장소에는 iOS 앱의 첫 구현 단위와 단위 테스트 소스가 있다. 실제 iOS 빌드 환경 검증은 남아 있다.
- 프로젝트 목적은 그룹 캘린더 iOS 앱으로 확정했다.
- 원래 MVP 기능은 유지하되 내부 검증 단계와 출시 준비 단계로 나눈다. 결제나 Apple/Google 연동을 완료하지 않은 내부 버전을 전체 MVP 완료로 간주하지 않는다.
- 대상 플랫폼은 iOS로 확정했다. SwiftUI/iOS 17과 EventKit을 첫 구현 기준으로 사용한다. 서버 및 인증 기술과 기간은 추후 확정한다.

## 작업 순서와 완료 기준

| 단계 | 작업 및 산출물 | 완료 기준 |
|---|---|---|
| 0. 범위 확정 | 앱/MCP 목적, iOS/웹 등 대상 플랫폼, 첫 캘린더 제공자, 인증 방식 결정. 화면 흐름과 정책 결정 기록 | 아래 정책 질문과 플랫폼 선택에 답하고 구현 범위를 확정 |
| 1. 실행 기반 | 선택한 스택으로 `src/new/` 구성, 실행 안내, 환경 변수 예시, 테스트 환경, 데이터 스키마와 마이그레이션 마련 | 새 환경에서 문서대로 실행 및 기본 검사 성공. 비밀 정보는 저장소에 포함하지 않음 |
| 2. 핵심 흐름 구현 | 테스트용 캘린더 어댑터로 사용자·Party 생성/초대/탈퇴, 공개 설정, 공통 시간 계산, 제안/응답/확정을 연결 | 서로 다른 사용자 3명이 가입부터 약속 확정까지 진행. 권한 및 공개 범위 테스트 통과 |
| 3. 외부 캘린더 연동 | 첫 제공자 읽기/쓰기 연동 후 두 번째 제공자 추가. 반복/종일 일정, 변경·삭제, 권한 철회, 재시도 처리 | 실제 계정으로 불러오기와 확정 일정 반영 검증. 재시도에도 중복 생성되지 않음 |
| 4. 공유와 알림 | 일정 변경 갱신, 초대·제안·변경·취소 알림, 오프라인 복귀 처리, 동기화 상태 표시 | 두 기기에서 변경 전달 확인. 실패 후 복구 및 중복 알림 방지 검증 |
| 5. 요금제와 결제 | 무료 Party 제한, Premium 권한, 대상 플랫폼 결제 연결, 구매 복원 및 구독 상태 반영 | 결제 테스트 환경에서 구매·복원·만료·취소/환불에 따른 권한 전환 확인 |
| 6. 통합 검증 | 핵심 화면 완성도 점검, 전체 사용자 시나리오, 계정 삭제/연결 해제, 운영 및 복구 안내, 사용 지표 수집 | 아래 출시 검증 시나리오 통과, 주요 결함 해소, 미해결 제약 기록 |

각 단계는 앞 단계의 완료 기준을 통과한 뒤 진행한다. 2단계는 내부 사용성 검증 지점이며 외부 서비스 연동 완료를 의미하지 않는다.

## 구현 전 결정할 정책과 권장 초안

다음은 확정된 요구사항이 아닌 논의용 기본안이다.

- 계정/권한: 2단계에 실제 로그인·세션 유지·프로필 편집과 방장/일반 멤버 권한 구현을 포함한다. 로그아웃 후 접근 거부와 방장 전용 작업의 권한 검증을 완료 기준에 포함한다.
- 변경/취소: 3단계에 확정 일정의 변경·취소 및 외부 캘린더 갱신·삭제를 포함한다. 부분 실패와 재시도 검증 후 4단계 변경/취소 알림에 연결한다.
- Premium: 원본의 반복 일정·고급 공개 설정·고급 알림·복수 캘린더가 출시 MVP에 포함되는지 0단계에서 명시한다. 외부 반복 일정 불러오기와 앱에서 반복 약속 생성은 별개로 구분한다. Widget은 원본대로 향후 범위다.

- 공개 범위: Party별 기본값은 Busy Only. 상세 공개는 명시적으로 선택한다. 숨김 일정은 해당 Party의 표시와 가능 시간 계산에서 모두 제외한다는 초안을 검토한다. 제외 시 실제 일정 충돌이 생길 수 있으므로 의미를 설정 화면에서 설명한다. “가능 시간만 공유”는 별도 정책이 필요한지 확정한다.
- 공통 시간: 검색 기간, 멤버별 활동 가능 시간, 약속 길이, 시간대를 입력으로 사용한다. 각 멤버의 가능 구간에서 Busy 구간을 빼고 교집합을 구한다. 일정이 비어 있다는 이유로 하루 전체를 가능 시간으로 처리하지 않는다.
- 제안: 제안 시 참여자 명단을 고정하고 전원 수락 시 확정한다는 초안을 사용한다. 거절 후 재제안, 응답 기한, 탈퇴자의 기존 제안 처리와 확정 일정 편집 권한은 구현 전에 결정한다.
- 확정: 확정 직전 최신 일정으로 충돌을 재확인한다. 앱 내부 확정과 개인 캘린더 반영 상태를 분리하고 사용자별 실패를 표시한다.
- Party: 초대 만료·재사용 정책, 방장 탈퇴 시 위임/해산, 무료 2개 제한에 참여 Party도 포함하는지 결정한다.
- 동기화: 플랫폼별 백그라운드 제약을 확인한 후 “즉시 반영”의 목표 지연과 수동 새로고침 동작을 정한다.

## 구현 구조

- `src/base/`: 기존 구현이 있을 경우 그대로 실행할 수 있도록 보존한다. 현재 기존 코드는 확인되지 않았다.
- `src/new/`: 신규 구현. 일정 계산·공개 정책·제안 상태 전이 같은 핵심 로직과 UI, 저장소, 외부 연동을 분리한다.
- 캘린더 어댑터: 테스트용/Google/Apple 구현이 동일한 읽기·반영 계약을 따르게 한다. 구체 API와 지원 범위는 플랫폼 결정 후 공식 문서로 검증한다.
- 주요 데이터: User, Party, Membership, CalendarConnection, Event, PartyCalendarVisibility, Proposal, ProposalResponse, CalendarWriteJob, Subscription. 제안 상태와 외부 캘린더 쓰기 상태를 별도로 관리한다.
- 접근 권한과 공개 필터는 데이터 반환 경계에서 적용한다. Busy Only 응답에는 제목·설명·장소가 포함되지 않도록 검증한다.
- 저장 시각과 사용자 표시 시간대를 구분하고, 종일/반복 일정은 원래 시간대 정보를 보존한다.

## 검증 계획

- 단위 검증: 겹침·인접 구간, 날짜 경계, 시간대/서머타임, 종일·반복 일정, 공통 시간 없음, 약속 길이 미달, 숨김 정책.
- 통합 검증: 다른 Party 접근 거부, 초대 만료, 탈퇴 직후 접근 차단, 응답 동시 처리, 중복 확정 방지, 캘린더 반영 재시도와 중복 방지.
- 출시 시나리오: 3명 초대 → 서로 다른 공개 설정 → 일정 불러오기 → 공통 시간 선택 → 제안 → 전원 수락 → 개인 캘린더 반영 → 변경/취소 → 알림 확인.
- 실패 시나리오: 연동 권한 철회, 제공자 오류, 일부 멤버 반영 실패, 기기 오프라인, 확정 직전 일정 충돌.
- 제품 검증: Party 생성, 캘린더 연결, 공통 시간 검색, 제안, 확정, 무료 제한 도달, 유료 전환 이벤트를 정의한다. 일정 제목 등 개인 내용은 분석 로그에 포함하지 않는다.

## 작업 운영과 다음 작업

- 초기 MVP는 AGENTS.md에 따라 main에서 작업한다. 이후 기능은 기능별 브랜치에서 구현·검증 후 병합한다.
- 현재 체크아웃 브랜치는 `master`다. 구현 착수 시 이력과 원격 브랜치를 확인하고 main 작업 기준에 맞춘다. 이번 계획 작성에서는 브랜치를 변경하지 않았다.
- 매 작업 시작 시 `docs/progressing.md`를 읽고, 종료 시 진행 중/다음 작업/차단 요소를 갱신한다.
- 코드 변경마다 관련 검사를 실행하며 완료 내용은 `docs/rec/YYYY-MM-DD_HHMM_설명.md`로 기록한다.
- 작업 종료 전 서브 에이전트가 변경 코드와 문서를 재검토한다.
- 현재 첫 구현 단위로 SwiftUI 앱 골격, 메모리 기반 데모 Party, 공통 가능 시간 계산, 약속 제안, EventKit 읽기 경계를 추가했다.
- 바로 다음 작업은 macOS/Xcode에서 프로젝트 생성·빌드·테스트를 검증하고, 남은 0단계 정책과 서버/인증 기술을 확정하는 것이다.
